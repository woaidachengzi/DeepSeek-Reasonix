# 抖音直播弹幕：一次真实操作记录

记录日期：2026-10-23。用户明确要求发送一次「暗信是不是好打些」，并记录步骤供 Reasonix 后续参考。

## 实际结果

已在抖音当时打开的「eStar.月亮（国服李信）」直播间发送一次指定文字。发送后输入框恢复占位提示，随后重新读取的聊天列表出现本账号昵称及完整原文「暗信是不是好打些」。没有再次发送，也没有发送先前截图中的另一句话。

本次由 Codex 的 `cua_repl` 原生应用控制完成，不是由 Reasonix 0.1.48 的 `computer_use` 完成。不能把这次成功当作 Reasonix 当前实现已经通过验收。

## 成功步骤

1. 选择抖音原生应用，读取当前窗口的可访问性树；确认正在操作用户所指的直播间。
2. 在当前观察中查找语义为文本输入区、占位提示为「与大家互动一下…」的控件。不要选择礼物、关注按钮或其他输入区。
3. 点击该输入区，再读取状态，检查焦点和输入内容。直播视频及其他观众的消息会继续变化，不需要等待整个窗口静止。
4. 填入用户指定的完整原文；发送前必须读取输入框实际内容，确认没有缺字、重复文字或旧草稿。
5. 只在原文已核对、目标直播间仍正确且输入框保持焦点时，按一次 Return 发送。
6. 发送后检查输入框是否清空，并重新读取消息列表，查找本账号的新消息及完整原文。仅按过回车或仅看到输入框清空，不能单独作为成功证明。
7. 若结果不明确，先读取状态、查找回显和错误提示，不自动重复发送。

## 本次使用的 API 与遇到的问题

实际调用顺序为：

```text
cua.getApp("抖音")
app.click(本次观察到的弹幕输入区)
app.getAXState()
app.typeText("暗信是不是好打些")
app.getAXState()
app.getScreenshot()
app.paste("暗信是不是好打些")
app.getAXState()
app.pressKey("Return")
app.getAXState()
app.getAXState()
```

- 第一次 `typeText` 后，输入框仍为空，未发送。通过状态与截图确认后，使用原生 `paste` 成功填入中文，再核对全文。
- `paste` 是本次工具提供的操作能力，不是 Reasonix 当前公开的操作参数；不能直接照搬不存在的 API。
- 本次输入区曾对应节点 253，但节点编号只属于当时的观察。后续必须重新定位，不能把 253、截图坐标或旧观察回执当作固定配置。
- 首次点击后的焦点报告一度指向直播网页根节点，之后才明确指向文本输入区。因此点击返回不代表已经可输入，输入返回也不代表文字已落入目标控件。
- 视频、在线人数及弹幕列表在整个流程中持续变化，操作仍可完成。关键是目标窗口、直播间、输入区、焦点与待发送内容可核对。

## 给 Reasonix 的复用说明

> 在用户明确指定的抖音直播间发送用户给出的原文。先观察当前窗口，定位「与大家互动一下…」文本输入区，点击并检查焦点；填入原文后读取输入框核对。确认目标直播间和内容都正确后，只发送一次；随后核对本账号的消息回显。无法确认结果时不要重发，也不要把其他观众相似的消息算成自己的发送成功。
>
> 如果工具返回 `state_changed` 且没有派发输入，说明本次没有点击或输入成功。检查新观察中的目标及内容；不要反复重试整个直播画面的旧回执，也不要声称其他操作能绕过当前实现的校验。

## Reasonix 0.1.48 的已核对限制（记录当时状态）

`internal/computeruse/computeruse.go` 的观察摘要包括完整原生状态和截图像素；`frame.go` 仅排除有明确 AX 几何信息的细小光标闪烁区域。操作前重新观察并比对摘要，任何其他差异都会返回 `state_changed`，不发送输入。

这意味着直播视频刷新、其他观众消息或在线人数变化，都可能使回执失效，即使弹幕输入框没有移动。截图中 Reasonix 所说的「直接打字不依赖画面比对」不符合当前代码：`type` 和 `key` 也经过同一验证。

后续修复需要验证操作目标、窗口身份、几何和焦点的稳定性，而不是要求整个直播窗口像素不变。仍应拒绝目标位置或内容变化、焦点转移、遮挡、窗口替换、过期/跨会话回执及不确定操作的重复派发；不能直接关闭状态校验。

本记录只提供已成功的原生操作流程与当前实现差异，没有宣称上述实现限制已修复，也没有测试当前 Reasonix 在真实直播间重新发送。

## 2026-10-24 输入校验修正

源码已为浏览器未提供 AX 光标坐标的情况增加键盘输入例外：完整原生状态、窗口、焦点、选区和内容必须一致，截图差异必须符合输入框内细窄插入光标的形状，且不能包含该光标压缩区域以外的变化。此例外用于 `type`、`key`，不放宽坐标点击或滚动的检查。

原生组件会在派发键盘事件前再次核对焦点及内容摘要，普通文本框的完整内容摘要可检测显示前缀之外的变化。`type` 返回 `input_verification=confirmed` 表示回读内容符合预期编辑；`unconfirmed` 表示需要检查返回的控件、截图或重新观察，不能自动重打。收件人转换为标签等界面行为可能需要视觉确认。

被拦截时使用 `blocked_reason` 区分回执失效、窗口或焦点变化等原因；`state_changed=true` 表示没有派发输入。直播视频等广泛画面变化仍需目标级校验的后续修复，本次修正尚未在真实直播间重新发送弹幕验收。

## 2026-10-24 首次打开会话的授权接线

0.1.50 修正了 Tauri 冷启动打开会话时遗漏交互授权初始化的问题。首次打开与设置重建均安装同一类授权服务；Yolo 不能代答应用访问授权。回归测试通过实际会话工厂打开会话，再由模拟工具请求应用授权，全程不观察或输入真实应用。

缺少授权处理器现在明确作为宿主配置拒绝返回，不表示 macOS 权限被收回。系统策略要求停止桌面输入，不能转用 JXA、CGEvent 或剪贴板探测。交互宿主管理的 Bash 调用会在启动进程前拒绝直接 `osascript`、已识别的内联 UI 自动化调用及常见 shell 包装。这是执行路径约束，不是对任意外部脚本、动态程序的完整系统沙箱。

发现输入落入其他应用时应立即停止输入，报告可能的影响，再通过原生工具重新观察目标。脚本退出成功、空剪贴板均不能证明目标字段已正确输入或输入失败。

新增桌面控制策略有意将固定系统提示从 3218 字节增至 4101 字节。随附更新系统提示、模型请求和前缀哈希快照；工具 schema 快照不变。升级时旧的模型前缀缓存会失配一次，相同配置后续构建仍保持字节稳定。

## 2026-10-24 观察回执与模型耗时

后续主屏失败记录中，动作返回的是 `observation_expired`、`dispatched=false`，并非已发送点击后页面无响应。相邻模型轮次约 38–41 秒，超过原有 30 秒回执期限。副屏观察也已返回窗口图像和 `x=-1920` 的边界；这些记录不足以判定副屏坐标或系统输入通道损坏。

0.1.51 将期限改为 120 秒，并返回 `observation_ttl_ms`；过期回执另含年龄和 `next_action=observe`。操作前仍重新抓取、比较原生状态与画面，并在比较后再次检查期限。移屏、焦点/窗口身份/内容变化、回执重用和过期均不能直接派发输入。模型须使用窗口内点坐标，不能因窗口位于负坐标显示器而改传绝对屏幕坐标。

同版新增 **设置 → 诊断 → AI 诊断日志**，可导出当前会话的详细或简洁记录。详细记录包含渠道返回的思考文本及完整本地工具结果，明确区分模型陈述、工具执行完成、输入派发与字段验证；附带近期工具耗时和安装包构建标识。范围、脱敏和时间线限制见 [AI 诊断日志说明](AI_DIAGNOSTIC_LOGS.zh-CN.md)。

通过 `use_capability` 调用的电脑控制结果也保留本次 `dispatched`、拒绝原因和输入回读状态，不再用“重复结果已省略”替代；重复指纹仍计入循环检测。原始主屏两帧离线重放证明旧期限拒绝 41 秒响应、新期限通过即时状态和像素复核后允许一次模拟点击，不代表真实邮箱输入已验收。另有负坐标/主屏 41–95 秒、移屏拒绝及新观察恢复测试。

授权卡片主按钮改用更具体的样式选择器和主按钮前景/背景 token，避免通用按钮继承色覆盖文字；共享的审批、回答和 MCP 主按钮均使用该修复。


## 2026-10-24 坐标点击投递路径

后续记录已出现 `dispatched=true`，但页面未改变。原坐标分支使用 `CGEventPostToPid`，只将事件发给进程；本地只读事件检查显示其 Cocoa 窗口编号为 0。补上窗口编号的实验仍未能通过窗口内坐标路由验证，因此未采用该实验实现，也未引入私有 API。

0.1.52 的坐标点击改经 WindowServer 正常前台鼠标路径。保持原来的应用授权、单次回执、画面比较及前台检查；额外核对落点的最前窗口 PID/ID、AX 命中元素所属应用/窗口、焦点窗口、PostEvent 权限和物理左键状态。覆盖、归属不明或权限不足时拒绝全部鼠标事件。只有预检通过才发送移动、按下、松开，鼠标将移至目标点。预检仅接受已授权、已激活的可见窗口，不自动恢复鼠标到其他应用。人或其他进程仍可能在预检与事件处理之间改变界面，不能承诺系统级原子操作。

日志增加 `dispatch_method=window_server_mouse`，简洁导出也保留。`dispatched` 仍表示投递，不代表网页已接受或任务成功。`pointer_target_changed`、`pointer_target_unverified`、`pointer_busy`、`input_permission_missing` 均须先解决原因并重新观察，不能盲目重复点击。

验收夹具新增独立坐标按钮计数，初始焦点固定在非文本视图，避免把本来已有焦点的输入框当作坐标点击成功。原生测试验证事件封装、窗口遮挡/负坐标以及预检拒绝零事件；测试回调不发送真实输入。当前测试进程没有辅助功能及 PostEvent 权限，尚未完成新路径的系统投递、Chromium 网页或真实邮箱端到端验收。

## 2026-10-24 双屏实际点击验收与覆盖层修正

0.1.53 进一步修正了矩形覆盖判断：Dock 与其他应用的点击穿透层可以覆盖整屏，却不是鼠标事件目标。改用公开的 AppKit mouse-down 窗口查询，核对准确窗口 ID、CG 所有者/层级/边界及 AX 前台焦点窗口。没有按应用名字跳过覆盖层；真实接收输入的其他窗口仍拒绝。网页 AX 叶节点不再必须提供 AXWindow，窗口身份由系统鼠标目标与批准应用的焦点窗口共同确认。后台 Go 进程通过 NSApplicationLoad 惰性建立只读查询环境，不激活窗口。

经用户临时授权，独立本地夹具在主屏、负 X 副屏分别验证原生按钮和 WKWebView 按钮各收到一次点击。测试后已移除临时权限并只读确认失效。完整范围和回显计数见[验收记录](evidence/2026-10-24-pointer-dual-display/README.md)。尚未验证 Chromium、真实邮箱、打字或完整 agent/审批链；本结果不能代替这些验收。
