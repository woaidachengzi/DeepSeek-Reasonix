# 抖音直播弹幕：一次真实操作记录

记录日期：2026-10-23。用户明确要求发送一次「暗信是不是好打些」，并记录步骤供 Reasonix 后续参考。

## 实际结果

已在抖音当时打开的「eStar.月亮（国服李信）」直播间发送一次指定文字。发送后输入框恢复占位提示，随后重新读取的聊天列表出现本账号昵称及完整原文「暗信是不是好打些」。没有再次发送，也没有发送先前截图中的另一句话。

本次由 Codex 的 `cua_repl` 原生应用控制完成，不是由 Reasonix 0.1.48 的 `computer_use` 完成。不能把这次成功当作 Reasonix 当前实现已经通过验收。

## 成功步骤

1. 选择抖音原生应用，读取当前窗口的可访问性树；确认正在操作用户所指的直播间。
2. 在当前观察中查找语义为文本输入区、占位提示为「与大家互动一下…」的控件。不要选择礼物、关注按钮或其他输入区。
3. 点击该输入区，再读取状态，检查焦点和输入内容。直播视频及其他观众的消息会继续变化，不需要等待整个窗口静止。
4. 填入用户指定的完整原文；发送前必须读取输入框实际内容，确认没有缺字、重复文字或旧草稿。
5. 只在原文已核对、目标直播间仍正确且输入框保持焦点时，按一次 Return 发送。
6. 发送后检查输入框是否清空，并重新读取消息列表，查找本账号的新消息及完整原文。仅按过回车或仅看到输入框清空，不能单独作为成功证明。
7. 若结果不明确，先读取状态、查找回显和错误提示，不自动重复发送。

## 本次使用的 API 与遇到的问题

实际调用顺序为：

```text
cua.getApp("抖音")
app.click(本次观察到的弹幕输入区)
app.getAXState()
app.typeText("暗信是不是好打些")
app.getAXState()
app.getScreenshot()
app.paste("暗信是不是好打些")
app.getAXState()
app.pressKey("Return")
app.getAXState()
app.getAXState()
```

- 第一次 `typeText` 后，输入框仍为空，未发送。通过状态与截图确认后，使用原生 `paste` 成功填入中文，再核对全文。
- `paste` 是本次工具提供的操作能力，不是 Reasonix 当前公开的操作参数；不能直接照搬不存在的 API。
- 本次输入区曾对应节点 253，但节点编号只属于当时的观察。后续必须重新定位，不能把 253、截图坐标或旧观察回执当作固定配置。
- 首次点击后的焦点报告一度指向直播网页根节点，之后才明确指向文本输入区。因此点击返回不代表已经可输入，输入返回也不代表文字已落入目标控件。
- 视频、在线人数及弹幕列表在整个流程中持续变化，操作仍可完成。关键是目标窗口、直播间、输入区、焦点与待发送内容可核对。

## 给 Reasonix 的复用说明

> 在用户明确指定的抖音直播间发送用户给出的原文。先观察当前窗口，定位「与大家互动一下…」文本输入区，点击并检查焦点；填入原文后读取输入框核对。确认目标直播间和内容都正确后，只发送一次；随后核对本账号的消息回显。无法确认结果时不要重发，也不要把其他观众相似的消息算成自己的发送成功。
>
> 如果工具返回 `state_changed` 且没有派发输入，说明本次没有点击或输入成功。检查新观察中的目标及内容；不要反复重试整个直播画面的旧回执，也不要声称其他操作能绕过当前实现的校验。

## Reasonix 0.1.48 的已核对限制（记录当时状态）

`internal/computeruse/computeruse.go` 的观察摘要包括完整原生状态和截图像素；`frame.go` 仅排除有明确 AX 几何信息的细小光标闪烁区域。操作前重新观察并比对摘要，任何其他差异都会返回 `state_changed`，不发送输入。

这意味着直播视频刷新、其他观众消息或在线人数变化，都可能使回执失效，即使弹幕输入框没有移动。截图中 Reasonix 所说的「直接打字不依赖画面比对」不符合当前代码：`type` 和 `key` 也经过同一验证。

后续修复需要验证操作目标、窗口身份、几何和焦点的稳定性，而不是要求整个直播窗口像素不变。仍应拒绝目标位置或内容变化、焦点转移、遮挡、窗口替换、过期/跨会话回执及不确定操作的重复派发；不能直接关闭状态校验。

本记录只提供已成功的原生操作流程与当前实现差异，没有宣称上述实现限制已修复，也没有测试当前 Reasonix 在真实直播间重新发送。

## 2026-10-24 输入校验修正

源码已为浏览器未提供 AX 光标坐标的情况增加键盘输入例外：完整原生状态、窗口、焦点、选区和内容必须一致，截图差异必须符合输入框内细窄插入光标的形状，且不能包含该光标压缩区域以外的变化。此例外用于 `type`、`key`，不放宽坐标点击或滚动的检查。

原生组件会在派发键盘事件前再次核对焦点及内容摘要，普通文本框的完整内容摘要可检测显示前缀之外的变化。`type` 返回 `input_verification=confirmed` 表示回读内容符合预期编辑；`unconfirmed` 表示需要检查返回的控件、截图或重新观察，不能自动重打。收件人转换为标签等界面行为可能需要视觉确认。

被拦截时使用 `blocked_reason` 区分回执失效、窗口或焦点变化等原因；`state_changed=true` 表示没有派发输入。直播视频等广泛画面变化仍需目标级校验的后续修复，本次修正尚未在真实直播间重新发送弹幕验收。
